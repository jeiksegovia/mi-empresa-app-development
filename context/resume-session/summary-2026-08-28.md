## 3) Insights, learnings, patterns (the point of this file)

### 3.1 — `window.open` must be synchronous with the click, or Chrome blocks it
Any `setTimeout`, `await fetch(...)`, or other async gap between the click and `window.open()` gets treated as a popup and silently blocked. Call it **first**, in the same event-handler tick, then do async work inside the new tab (it does its own `GET /centro-costos/items/:id`). If `window.open()` returns `null` (blocked anyway, e.g. a hardened browser profile), fall back to in-tab `navigateTo`.

### 3.2 — "Which tab am I?" needs two signals, not one
`window.opener` is the obvious way for a spawned tab to know it can `window.close()` itself, but some Chromium builds/test harnesses drop it. Pattern used here: pass `?popup=1` in the URL when opening programmatically, and treat `window.opener && !window.opener.closed` **OR** `?popup=1` as "safe to close." Belt-and-suspenders for a browser API with build-to-build behavior drift.

### 3.3 — A disabled retry button is not the same as a working retry
The first `window.print()` always worked; a second call after Cancel/idle silently no-op'd. Fix: `window.focus()` immediately before `print()`, defer the call by ~50ms (lets a just-dismissed OS dialog fully close), and gate repeat clicks with a **client-side cooldown timer** (1.5s here) rather than trying to detect "the dialog closed" (no reliable event for that). The cooldown also solves double-click debouncing for free.

### 3.4 — `fullPage: true` screenshots lie about print layout
A Playwright `page.screenshot({ fullPage: true })` under `@media print` emulation captures the **whole flex-column document height**, including any `min-h-screen` wrapper that print CSS didn't explicitly collapse — producing a preview that looks like a huge blank page with the ticket crammed in one corner, even though the *actual* printer output (paper size = content size for thermal rolls) would be correct. Fix: explicitly zero out `min-height`/`height` on the layout shell under `@media print`, and screenshot the specific page-container `data-testid` locator instead of `fullPage`.

### 3.5 — Two borders touching look like one thick line, and it's confusing to debug
A "double line" under a table row was actually the row's own `border-bottom` sitting directly against the next row's `border-top` (a visually-emphasized total row). Don't touch the summary row — suppress the border on the row **immediately before** it: `.row:has(+ .total-row) { border-bottom: none }`. Generalizes to any adjacent-border artifact.

### 3.6 — A "missing field in the UI" is often a swallowed 403, not a template bug
The recibo header (empresa name/NIT/address) was blank for CONTRATOS. The instinct is to suspect the Vue template. The actual cause: `GET /empresa` was `requireRole('ADMIN')`-gated, and the page's fetch had `.catch(() => null)` — a completely silent failure path. **Always check the network response before touching markup** when a field that should render just doesn't.

### 3.7 — Route-level RBAC exceptions beat matrix flips for "read is different from write"
Two precedents now in this codebase for "some roles need read but not write on a domain that's otherwise `false`": `/empresa/cargos` (GET+POST for CONTRATOS, contract D1) and now `GET /empresa` root (every authenticated role, DTO split by ADMIN-vs-not). Both explicitly **do not** touch `DOMAIN_ACCESS[tipo].empresa`, which stays `false` — that constant governs writes and other empresa sub-resources. When you need "everyone reads, only ADMIN writes," reach for a route-level branch + response-shape split, not a matrix-wide `true`.

### 3.8 — Never ship `src/generated/prisma/` in a CodeDeploy zip
It's gitignored on purpose. It contains a **platform-specific native query-engine binary** — building locally on macOS arm64 produced a `.dylib.node` that is useless (and would silently crash) on the Linux instance. It also bloated a 287 KB artifact to 12 MB for nothing: `after-install.sh` step [4/6] already runs `npx prisma generate` on-instance. If a deploy zip is suddenly huge, check for this first.

### 3.9 — This machine's `aws` CLI has no implicit default profile
Every single `aws` invocation needs `--profile disruptive` explicitly — including ones you'd expect to inherit from a prior successful call in the same shell session. One `aws s3 cp` was typed without the flag (copy-paste from a version that had it) and failed with `Unable to locate credentials`, even though the identical command with `--profile disruptive` two lines later succeeded. SSH-based `aws` calls on the instance itself work without a profile flag (instance role) — don't let that pattern bleed into local-machine commands.

### 3.10 — Local dev-DB drift from manual `curl PUT` testing poisons the *next* automated run
Earlier LAN-printer testing manually flipped `centro.habilitarRecibo = true` via `curl PUT` on a seeded centro. Hours later, an unrelated smoke test asserting "all seeded INGRESOS centros have `habilitarRecibo === false`" failed — not a regression, just forgotten manual state. **Reset any manually-toggled flag before trusting a subsequent test failure as a real signal.** Consider: a dedicated "reset local fixtures" script would have caught this faster than re-deriving it from a stack trace.

### 3.11 — Reuse dual-mode (env-var-driven) Playwright specs for staging QA; don't write curl one-offs
`ocultar-beneficiario.spec.ts` already read `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `TEST_API_URL` from env with local defaults — pointing it at staging needed **zero code changes**, just different env vars, and it ran 2/2 first try. When a bug fix needs staging confirmation, check for an existing dual-mode spec before reaching for curl; if none exists, write one that takes env vars from the start (see `ocultar-beneficiario-empresa-ui.spec.ts`, written fresh this session with staging in mind from line 1) — it becomes a permanent regression check, not a throwaway.

### 3.12 — Resolve UI elements by ID from the API, not by DOM-text proximity
An early draft of the staging UI spec tried to find "the Valoraciones card" via a fragile `page.locator('div', { has: page.getByText(...) })` ancestor filter — it silently matched zero elements. Fixed by fetching the centro's numeric ID via a real `GET /centro-costos?tipo=INGRESOS` call first, then using the app's existing deterministic `data-testid="centro-costos-grupo-header-${id}"` pattern. Prefer "ask the API for the ID, then use the app's own testid convention" over DOM-text heuristics whenever the app already exposes stable IDs.

### 3.13 — `ADD COLUMN ... NOT NULL DEFAULT false` is safe on populated tables (contrast with RB-1)
A recurring worry in this codebase (see the `centro-costos-ago-5` runbook's RB-1) is `NOT NULL` columns added without a default breaking on tables with existing rows. `ocultar_beneficiario` sidestepped that entirely by including `DEFAULT false` in the same `ADD COLUMN` statement — no 3-step nullable→backfill→enforce dance needed. The 3-step pattern is only required when the new value must be **computed from existing data** (like `fecha := periodo` in aug-17); a constant default doesn't need it.
